# Audit of the 355-byte MX-1 UAC2 descriptor candidate

## Decision

The generated 355-byte high-speed descriptor has no identified structural blocker for an Apple-oriented UAC2 experiment. Its audio graph, clock references, alternate settings, endpoint identities, and length fields are internally consistent. This conclusion covers descriptor structure and the cited host requirements. It does not establish that the MCU's endpoint loader, control requests, sample pump, or physical link meet them.

Integration requires the new class-request handler, capture-first startup, replacement of the old fixed-offset descriptor initialization, and a relocated descriptor pointer. Those changes are now present in the separate offline device-probe build; its emulation evidence is summarized below. The original full-speed configuration does not supply class-compliant audio. Windows' in-box UAC2 driver is not a suitable audio test for this implicit-feedback design.

Audited fixture: `research/usb_sources/uac2-preserve-modes-design.json`, generated by `tools/uac2_design.py --variant preserve-modes`. Tests: `tests/test_uac2_design.py`.

## Byte and graph checks

The total configuration length is `0x0163` (355), with four interfaces. The IAD covers exactly IF0, IF1 and IF2; vendor MIDI IF3 remains outside the audio collection. The AudioControl class-specific block occupies 75 bytes, equal to its own `wTotalLength`. All entities have distinct nonzero IDs.

| Entity | ID | Input/source | Clock | Descriptor role |
|---|---:|---:|---:|---|
| Clock Source | `0x10` | Internal | — | Fixed during a USB session |
| USB Input Terminal | `1` | USB OUT / IF1 | `0x10` | Playback entering the device |
| Physical Output Terminal | `2` | Entity `1` | `0x10` | Line connector output |
| Physical Input Terminal | `6` | Line connector input | `0x10` | Capture entering the USB audio function |
| USB Output Terminal | `7` | Entity `6` | `0x10` | USB IN / IF2 |

There are no dangling references, cycles, accidental Feature Units, or advertised terminal controls without a planned implementation. `0x0603` is used for the physical line connectors; it is a broad representation of the mixed audio paths and does not describe each real MX-1 jack separately. The function category is `0x0a`, professional audio. These values and field layouts match the upstream UAC2 definitions. [D1]

The audio alternates are:

| Interface/alternate | Channels | Data endpoint | Attributes | Maximum packet | Interval |
|---|---:|---:|---:|---:|---:|
| IF1 / 0 | Idle | None | — | — | — |
| IF1 / 1 | 18 | `0x0d` OUT | `0x05` | 1008 | 1 |
| IF1 / 2 | 2 | `0x0d` OUT | `0x05` | 112 | 1 |
| IF2 / 0 | Idle | None | — | — | — |
| IF2 / 1 | 18 | `0x8e` IN | `0x25` | 1008 | 1 |
| IF2 / 2 | 2 | `0x8e` IN | `0x25` | 112 | 1 |

Each active alternate declares Type I PCM, four-byte subslots, 24 significant bits, one data endpoint, and a UAC2 eight-byte class-specific endpoint descriptor. At 96 kHz, a nominal microframe holds 12 sample frames. Including one additional frame requires 936 bytes for 18 channels or 104 for stereo; both fit the preserved endpoint capacities. No high-bandwidth transaction multiplier is claimed.

The complete original 52-byte IF3 vendor-MIDI block is preserved byte for byte, including bulk alternate 0 (`0x03` OUT / `0x84` IN) and interrupt alternate 1 (`0x03` OUT / `0x85` IN). Those descriptors remain vendor-specific. Their presence preserves hardware endpoint configuration on which other firmware tasks may depend; it does not make MIDI class compliant.

## 18-channel and stereo alternates

The USB-IF specification expressly permits AS alternates with different channel clusters. Section 3.13.1.1 explains that hosts can derive the current cluster from the selected AS descriptor if optional Cluster Control is absent. Section 4.1 distinguishes the terminal's logical cluster from the stream's physical cluster. Thus, keeping one terminal link for both 18-channel and two-channel modes is appropriate; allocating different terminal IDs per alternate would break the one-interface/one-terminal relationship. [D2]

The current descriptor keeps 18 channels in the internal input-terminal declarations and has no Cluster Control. The active streaming descriptors state the actual transport width. Main-pump disassembly at `0x01009840` independently checks the OUT and IN alternate bits in register `0x4001017c`; alternate 2 selects internal channels 16/17 for both directions. No comparison requiring equal alternate numbers was found. Actual-Thumb cases in `sources/hardware/uac2_pump_harness.py` confirm independent 18/2-word transfers in both mixed combinations, IF1=1/IF2=2 and IF1=2/IF2=1; original and patched duplex traces match in that model. However, OUT packet-tail accounting subtracts 72 bytes regardless of stereo mode. The explicit readiness/phase model does not certify real packet boundaries, so both mixed combinations and stereo-only operation still need a physical audio test.

XMOS' own USB audio implementation provides a practical comparison: its ADAT mode varies playback channel counts through alternate settings. It is supporting evidence that channel-count changes are normal UAC2 behavior, not proof of MX-1 behavior. [D3]

## Clock controls

Clock `0x10` has `bmAttributes=0x01` and `bmControls=0x05`: internal fixed frequency, not SOF synchronized, with read-only frequency and validity. All four terminals reference this same clock. No mute, gain, latency, active-alternate, or valid-alternate class controls are advertised elsewhere. [D1]

The planned requests are frequency `GET_CUR`, frequency `GET_RANGE` containing one discrete current rate, and validity `GET_CUR`. Microsoft documents that a single fixed-frequency clock need not implement frequency `SET_CUR`. Its one range uses equal MIN/MAX and zero RES. [D4]

The handler must return the actual boot-selected hardware rate, honor shorter `wLength` requests, and stall unsupported writes/entities/selectors. A validity value of one is truthful only after the sample clock is running. If a physical control can change the clock while USB remains configured, the fixed-session assumption must be enforced or replaced with proper dynamic clock signaling. Do not advertise three selectable rates merely because the front panel can select three rates across different sessions.

## Implicit feedback and Apple startup

`0x05` marks asynchronous OUT data. `0x25` marks asynchronous IN data that also supplies implicit feedback. Both streaming paths share clock `0x10`. Apple supports this arrangement, including a 125 µs high-speed UAC2 interval, and requires consistent IN timing before it starts sending OUT data. [D5]

The hardware investigation found that the original pump's IN-start transitions depend on OUT activity. The proposed instruction change must remove that dependency while preserving the hardware IN readiness and buffer requirements. A mock demonstrating the state transition is useful; a physical trace must still show correctly timed IN packets and sustained output when no OUT audio has yet arrived. Start capture-only, playback-only, and duplex separately, then repeat start/stop and reconnect.

Windows' in-box UAC2 driver explicitly requires an explicit feedback endpoint for asynchronous OUT and does not support implicit feedback. A Windows failure would therefore not establish an Apple failure. Universal desktop class compliance would require a further transport change. [D4]

## Device identity, qualifier, and full speed

The candidate device descriptor and qualifier both use class/subclass/protocol `EF/02/01`. UAC2 sections 4.2 and 4.3 require those values for IAD-aware enumeration. Their USB revision remains 2.00, EP0 size 64, and configuration count one. [D2]

The original 45-byte alternate-speed template contains four inactive vendor interfaces, with no audio endpoints. Keeping it is an explicit **unsupported full-speed audio behavior**, not a UAC2 fallback. The integrated request emulator executes the stock dispatcher and confirms that `GET_DESCRIPTOR(OTHER_SPEED_CONFIGURATION)` returns descriptor type 7 for both simulated speed settings, although the stored template begins with type 2. A physical attachment must still confirm the response on the wire and that full-speed operation does not activate high-speed DMA assumptions. Full-speed UAC audio support is outside this candidate.

Reusing `0582:01a3` keeps this private existing-device experiment recognizable, but an installed Roland Mac driver can be a competing match. Apple documents that ID-specific USB personalities can outrank a generic class match. The actual installed Roland personality has not been inspected here, so this is a **host test consideration**, not a demonstrated firmware blocker. Identify which driver attached, or use a clean class-driver test environment; do not infer native class compliance solely from successful playback through an installed Roland driver. [D6]

## Checks that must accompany the integrated build

The six descriptor-fixture tests pass, including exact original MIDI preservation, resolved graph references, maximum-rate packet capacity, and the IAD boundary. The integrated firmware should additionally be inspected for:

1. Descriptor pointer and length replacements pointing wholly inside the allocated region, without the old UAC1 fixed-offset sample-rate writes corrupting it.
2. Class requests reaching the real EP0 response/stall primitives with the correct setup fields and actual clock value.
3. Standard configuration/alternate requests retaining correct endpoint behavior for every advertised alternate.
4. Consistent wire descriptors at both speeds and bounded handling of unknown requests.
5. A real IN stream that starts first, uses the correct sample alignment, and continues without underrun or stale data.

Items 1–4 can be partly checked using static analysis and the emulated request/loader paths. Item 5 and complete enumeration require the device.

### Integrated offline checkpoint

`build/device-probe/arm-verification.json` records eight passing groups for the integrated build. Original ARM startup instructions copy the 900-byte SRAM extension and preserve the other initialized-data regions. The replacement initializer registers the new callback, relocates the configuration, and updates maximum packet sizes for 44.1, 48, and 96 kHz. Requests run through the original dispatcher to the compiled handler, including short reads and rejection paths. The original descriptor walker produces the same endpoint hardware-table writes as the stock image at all three rates and both speed settings. The backup initializer also retains its original descriptor and callback tables.

These checks stub RTOS task creation, low-level USB hardware startup, and final EP0 FIFO delivery. They do not emulate USB tokens, FIFO timing, physical sample-clock lock, or a host's enumeration policy. The handler's validity response reflects a supported configured sample rate rather than measured PLL lock. See the build's report and `tools/device_probe_verify.py` for the exact scope; this checkpoint is evidence for the implemented control path, not physical iOS compatibility.
